## 升级后的行为变化

- 旧 Web 登录 token 会失效，需要重新登录。
- 生产 ADMIN / SUPER_ADMIN 必须开启 TOTP。尚未绑定者登录后前往“审批中心”完成绑定，其他受保护 API 在此之前会拒绝访问。
- 历史飞书绑定没有“已确认”标记，会拒绝派单或控制命令。员工归属用户需要在管理页面重新保存绑定，明确确认 OpenID 与允许使用的群聊。首次 `@` 不能代替身份绑定。
- 生产必须配置三组独立随机值：`AIE_SECRET_MASTER_KEY`、`AIE_BACKUP_MASTER_KEY`、`AIE_SETUP_TOKEN`，以及强数据库密码和 HTTPS 公网地址。
- 现有数据库的密码不会因修改 `.env` 自动变化。先通过 PostgreSQL 的 `\password` 修改实际密码，再让连接配置与其一致。
- 文件 Vault 检测到错误密钥、损坏密文或加载失败时拒绝启动，避免把旧库当作空库覆盖。
- 远程注册命令使用服务端配置的 HTTPS 地址。9090 默认仅绑定回环；需要远程工作站时显式设置监听地址并限制防火墙来源。
- SFTP 目标需要补填可信主机指纹。请在备份主机控制台或其他可信渠道核对，不能把一次未经验证的网络探测视为身份确认。
- 历史远程软件发布在生产安装前需要有效签名。未提供签名的上游源会被拒绝；可二次认证后上传经审核的软件包。

## 新部署

1. 为域名配置 DNS，并准备可信 HTTPS 入口。可使用仓库的可选 Caddy gateway，或已有 HTTPS 网关。
2. 使用固定版本/经过核验的镜像 digest。源码构建示例：

   ```sh
   docker build -f deploy/Dockerfile.server -t aie-control-plane:security-20261025 .
   docker build -f deploy/Dockerfile.admin -t aie-admin:security-20261025 .
   python3 deploy/generate-env.py --domain employee.example.com \
     --server-image aie-control-plane:security-20261025 \
     --admin-image aie-admin:security-20261025
   ```

   `generate-env.py` 仅适用于新安装：生成随机秘密、以 0600 权限保存，不覆盖已有文件，也不打印秘密值。生产制品宜使用 `repository@sha256:...`；本地构建标签不能替代发布制品的 digest 固定。

3. 检查环境文件和数据目录位置，再启动：

   ```sh
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml --profile public up -d
   ```

4. 经 HTTPS 打开管理页面，在首次设置页输入环境文件中的部署初始化密钥，然后完成管理员 TOTP 绑定。
5. 明确设置员工飞书绑定及群聊。配置飞书 HTTP 回调时同时配置 Encrypt Key；采用 WebSocket 模式不需要公开回调地址。

直接启动二进制的默认 HTTP/gRPC 监听也仅绑定回环；生产员工的默认 MCP 地址使用已配置的 HTTPS 公网地址。

默认端口：数据库不发布；8080/8088/9090 仅回环。`public` profile 的 gateway 发布 80/443（80 用于 HTTPS 跳转和证书验证）。默认 Docker 网段为 `172.30.20.0/24`，gateway 固定地址为 `172.30.20.10`；如与现有网络冲突，修改网段、gateway 地址和 `AIE_TRUSTED_PROXIES`，三者需要一致。

## 已有数据：先迁移密钥，不能直接替换变量

不要对已有部署直接运行新环境文件生成器，否则新旧密钥不同会导致旧数据无法解密。

1. 在可信离线位置备份数据库、整个服务器数据目录和现有环境文件。备份包含旧 CA/机密，应限制读取权限。
2. 停止全部控制面进程和相关调度入口；保持维护窗口，禁止新旧版本并发写入数据。
3. 运行数据库迁移至 `000035_security_hardening.sql`。该迁移会撤销旧明文 Web 会话，保留权限策略并建立持久化安全状态。它不会自动改变实际数据库密码或加密密钥。
4. 在权限为 0600 的私密环境文件中准备新密钥，同时提供 `AIE_OLD_SECRET_MASTER_KEY` 和 `AIE_OLD_BACKUP_MASTER_KEY`。命令使用现有 PostgreSQL 连接配置，不把密钥放在命令行参数里。
5. 先检查，再显式迁移：

   ```sh
   # 在 server 目录构建，也可使用新镜像中的 /app/security-migrate
   go build -o /private/tmp/aie-security-migrate ./cmd/security-migrate
   /private/tmp/aie-security-migrate --vault /实际数据目录/secrets/secrets.vault
   /private/tmp/aie-security-migrate --vault /实际数据目录/secrets/secrets.vault \
     --apply --offline-confirmed
   ```

   如果旧部署确实使用源码默认密钥，在两条命令中都显式加入 `--from-legacy-defaults`。如果旧备份使用了 `AIE_MASTER_KEY`，其实际值应作为 `AIE_OLD_BACKUP_MASTER_KEY`，不要误当作默认值。

   工具会检查所有旧密文，再迁移 Vault、数据库中的加密 TOTP 和备份目标配置，撤销旧会话，并保存旧加密 Vault 的私密恢复副本。默认不改写数据；`--apply` 才应用。

   文件与数据库不能通过一个跨系统事务同时提交。如果数据库提交报错或进程中断，保持服务器停止，核对数据库和工具保留的 Vault 副本后再恢复；不要盲目重跑。完整离线快照是恢复依据。

6. 把服务改为新密钥后启动；删除运行环境中的 `AIE_OLD_*`，保留旧密钥于离线恢复材料中。生产不再使用旧的 `AIE_MASTER_KEY` 别名。
7. 已有历史备份产物不会被迁移工具重写。常态下不配置旧密钥；确实需要恢复旧版加密备份时，在受控维护窗口显式提供 `AIE_BACKUP_PREVIOUS_KEY`。它只用于历史 v1 备份解密，新备份使用当前密钥和 v2 版本；恢复仍必须匹配数据库记录的摘要。完成后移除该变量。使用过公开默认密钥的历史备份应按已可能泄露处理并更换。
8. 重新登录，完成 TOTP、飞书绑定确认、SFTP 指纹配置，生成一份使用新密钥的备份。

## 资源上限

| 类型 | 上限 |
| --- | --- |
| 普通 API 请求体 | 2 MiB |
| MCP 请求体 | 8 MiB |
| 飞书 HTTP 回调 | 1 MiB |
| 工作流 ZIP 上传 | 32 MiB |
| 工作流 ZIP 文件数 / 单文件解压 / 总解压 | 2000 / 8 MiB / 128 MiB |
| 通用附件/产物上传 | 128 MiB（原有业务层更小上限继续适用） |
| 基础设施软件包上传 | 512 MiB，加 multipart 开销 |
| 备份产物 / 解压总量 / 文件数 | 128 MiB / 512 MiB / 10000 |
| 同时处理的非 GET 请求 / 大上传 | 32 / 2 |
| SSE | 每用户 4 个，总计 256 个，周期重新认证 |

这些上限是当前内存加密实现的明确保护边界。超出会失败，不会自动取消限制。较大规模备份需要后续采用经过设计的分块加密和流式方案；不能简单提高上限后宣称已解决内存风险。

## 软件发布信任

生产远程软件源需要：

- `AIE_SOFTWARE_ALLOWED_HOSTS`：明确的 HTTPS 主机列表，重定向也要符合规则。
- `AIE_SOFTWARE_SIGNING_KEY`：Base64 Ed25519 发布公钥。
- 远程 release 的 `signature` 字段：对 `ReleaseSigningPayload` 的签名，Base64 编码。

签名内容为八个 UTF-8 字段，以 LF 连接：`AIE-RELEASE-V1`、version、os、arch、url、转换成小写的 sha256、format、entry。应直接使用服务端导出的 `ReleaseSigningPayload` 构造相同字节，避免 JSON 序列化或空 entry 的差异。更换发布公钥属于部署信任变更，必须经受控渠道更新。

公钥、来源限制、摘要、二次认证共同保护远程安装；SSH/PVE 仍需要专用账号、最小权限及独立管理网。源码发布流程会生成 SBOM 与构建来源证明；实际镜像/依赖 CVE 扫描和镜像 digest 核验仍应作为发布流程的上线条件。
