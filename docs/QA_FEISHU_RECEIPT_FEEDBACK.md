# 飞书首次派单无反馈排查与修复

排查日期: 2026-10-20. 下列时间均为北京时间 (Asia/Shanghai).

## 实际记录

两次消息均已收到并创建独立任务, 第二次在第一条任务完成前排队等待.

- 第一次: `JOB-ff536ea8abd8f54f`. 11:25:19.320 创建, 11:25:20.081 进入运行, 11:25:45.531 记录首段回复, 11:26:25.605 完成. 总耗时约 66 秒.
- 第二次: `JOB-195e6809e6f4aa18`. 11:25:40.499 创建, 由于员工正在执行前一条而等待; 11:26:27.582 进入运行, 11:26:31.115 完成.
- 两次任务均有 CREATED、状态转换和最终回复记录, 均有独立飞书卡片 ID. 旧实现没有独立的回执送达时间记录, 无法由旧日志确定第一张卡片在飞书客户端实际何时显示.
- 后台任务列表仅首次打开/手动刷新时拉取任务, 会漏看页面打开后从飞书创建的任务. 任务详情虽有轮询, 但不会替任务列表加载新任务.
- 第一次执行期间没有工具进度摘要, 首段文本约在 26 秒后才到达服务端. 该现象不能推导出任务没有执行或第二条消息才触发第一条.

## 产生原因

任务列表未持续更新外部来源新建任务. 模型输出前缺少可持续变化的等待提示, 容易被误认为没有收单. 卡片刷新原先串行处理且没有独立请求超时, 存在某张卡片网络请求拖住其它卡片的风险; 这项风险无法由现有历史日志认定为本次第一张卡片未及时显示的唯一原因.

## 解决方案

1. 后台任务列表每 3 秒刷新, 页面恢复可见/重新聚焦时刷新. 请求不重叠, 离开页面后停止刷新, 页面隐藏时暂停轮询.
2. 执行中任务卡片每 10 秒更新已收单时长及无需重复派单提示, 不编造模型思考或工具活动.
3. 不同卡片最多 4 路并行刷新, 单张请求最长 12 秒; 同张卡片串行, 执行期间收到的新状态变更保留到下一次刷新.
4. 首张卡片使用稳定 UUID 重试, 避免网络响应丢失造成重复卡片. 成功后记录 FEISHU_RECEIPT 时间线事件与卡片 ID.
5. 服务重启仍补齐历史卡片最终状态; 执行中卡片优先刷新, 终态任务不再产生定时等待更新.
6. 本地运行时下载目录加入版本控制忽略规则, 避免把用户附件作为源码收录.

## 测试要点

1. 打开任务列表后从飞书创建任务, 无需手动刷新即可出现并更新状态. 切换浏览器标签页、恢复焦点、离开页面时刷新行为正确.
2. 模型长时间没有新文本时卡片显示实际收单时长, 不声称工具活动; 完成后停止等待提示.
3. 一张卡片网络请求挂起不阻塞其它空闲刷新槽位; 请求超时后可重试. 同一张卡片不能并发创建两次.
4. 首次发送期间任务已经完成, 后续刷新仍把最终状态写到原卡片, 不丢更新、不重复建卡.
5. 回执成功只写一条时间线; 重试 UUID 稳定. 服务重启后已完成任务仍能补上最终状态.
