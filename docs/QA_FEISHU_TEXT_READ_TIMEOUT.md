# 飞书附件读取超时修复验收

日期: 2026-10-20. 使用 Codex 默认文件处理能力, 已撤回小文本正文内联, 自建附件读取工具和额外 PDF 解析依赖.

## 产生原因

原任务 JOB-e39b478414f7eced 的图片和 test.txt 均已下载. TXT 大小 12 字节, 本地与服务端散列一致, 正文为 `测试文件`. 原生图片输入正常, 但读取 TXT 的命令启动失败:

```text
Failed to create unified exec process: timed out after 15000ms connecting runner pipe-in
```

故障发生在 Codex Windows 执行器启动阶段, 命令没有开始读取文件. AEW 原来在 Windows 服务会话 0 运行. 升级 Codex 后, 同一服务会话中还出现 workspace routing discovery timed out. 将同一个 AEW, 同一个 Codex 和同一模型放到已登录用户会话运行后, 默认执行工具及文件读取成功. 因此升级版本本身不足以解决此机器的服务会话问题, 运行会话是复测确认的环境差异.

模型回合正常结束会使任务显示完成, 这不代表模型请求的每一次工具操作都成功.

## 解决方案

1. 将 AEW 实际使用的独立 Codex 从 0.157.1 升级到稳定版 0.163.0.
2. 使用登录用户的 Windows 计划任务隐藏启动 AEW. 原服务停止并改为手动, 避免双实例和再次进入服务会话 0. 用户登录后自动启动; 用户注销会终止此执行环境.
3. 后续部署识别并保留该启动方式, 校验工作区路径和安装散列, 更新失败时恢复备份. 未配置用户会话启动的安装保留原服务部署分支.
4. 附件保留原有下载和本地路径传入方式, 图片使用原生图像输入. TXT, PDF 和大文件由 Codex 默认工具读取, 不新增平台专用解析器或全文注入.
5. Codex 子进程工作目录使用任务工作区, 工具失败状态如实记录. 本地诊断支持指定模型以复现员工的实际配置.

## 测试要点与结果

1. 已部署 AEW, 模型 gpt-5.6-luna, 使用默认终端读取原 12 字节 test.txt, 返回 `测试文件`, exitCode 0. 终端执行标识验证成功. 文件为无 BOM 的 UTF-8, Windows PowerShell 旧默认编码会显示乱码, 读取时需指定实际 UTF-8 编码.
2. 默认工具读取 2 MiB TXT 的开头, 中间及结尾标识, 三处均与生成时的预期值匹配. 未提前给模型标识值或文件正文.
3. 默认工具读取 40 页 PDF 的第 1, 20, 40 页, 三处标识均匹配. 本机默认环境使用已有 pdfinfo 与 Python/pypdf; 平台未添加解析依赖. 该验证覆盖文字型 PDF, 扫描件和所有格式不能由这次抽样验证推出.
4. 复测通过本地 AEW IPC 进入真实 Codex 运行链路, 仅提供路径和读取要求. 没有发送飞书测试消息, 没有改写用户原任务结果. 真实飞书新消息完整验收仍待用户发送.
5. 单元回归覆盖附件路径, 原生图片协议及后续回合隔离. 部署检查覆盖用户会话启动, 单实例, 连接状态和安装散列. 回滚与未配置计划任务的服务部署分支仅代码检查, 未故意制造部署失败或再次切回服务执行.

AEW 全部测试包通过. 附件下载包在受限沙箱内连接回环端口被系统拒绝, 在正常本机权限下重新执行通过. `git diff --check` 通过. 部署脚本实际重部署后, AEW 在用户会话 1 单实例运行, ready=true, reconnect=CONNECTED; 原 TXT 按 UTF-8 再次读取成功. 安装 SHA256 为 `9C99648EAF7DF7038043D041E185C79144732D735B5473D2F9BE0CD263174661`.

默认文件能力仍受模型上下文和本地可用工具约束. 大文件按任务选择范围或分段读取; 这次不另造平台文件读取协议, 也不承诺任意大小文件一次进入模型上下文.
